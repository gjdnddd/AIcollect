# 세션 프롬프트 모음

> **A** — 사용자가 매 세션 시작 시 붙여넣기  
> **B** — 작업별 규칙 (작업 유형 바뀔 때 해당 규칙 제공)  
> **C** — 맥락 관리 (계획서·맥락노트·체크리스트 MD 운영)  
> **레벨 1** — 핵심 규칙 (AI가 이상할 때 언제든 던지기)  
> **레벨 2** — 리마인드 프롬프트 (대화 오래됐을 때 던지기)

---

## 레벨 1. 핵심 규칙 (언제든 던지기)

> AI가 컨펌 없이 진행하거나, 모델 추천 안 하거나, 범위 벗어나기 시작할 때 그냥 던진다.

```
[핵심 규칙]
- 진행 전 반드시 모델 추천 + "Sonnet, 진행할까요?" 컨펌
- 작업 유형이 바뀌면 해당 규칙 달라고 요청하거나 직접 읽기
- 한 번에 하나의 작업만, 범위 벗어난 수정 금지
```

---

## 레벨 2. 리마인드 프롬프트 (대화 오래됐을 때)

> 20~30턴 이상 됐거나, AI가 이상한 방향으로 가기 시작할 때 던진다.  
> "현재 작업 목표" 한 줄은 사용자가 직접 채워서 던진다.

```
[리마인드]
지금까지 한 것 요약해줘.
그리고 아래 규칙 다시 지키면서 계속해:
- 진행 전 모델 추천 + "Sonnet, 진행할까요?" 컨펌
- 작업 유형 바뀌면 해당 규칙 확인 후 진행
- 범위 준수, 한 번에 하나의 작업만
현재 작업 목표: [여기에 한 줄 적기]
```

## A. 세션 시작 템플릿 (매 채팅창 붙여넣기)

```
[AI 첫 발화]
준비됐습니다. 목표를 말씀해주세요.

[목표를 들으면]
1. "기존 운영 중인 프로젝트인가요, 새로 시작하나요?" 묻는다.
   → 기존: 계획서·맥락노트·체크리스트 읽고 현재 단계·상태 보고 → 바로 재개
     (파일 경로를 같이 제공한 경우 바로 읽기. 없으면 "파일 경로를 알려주세요" 요청)
   → 신규: 0단계 시작
     a. 프로젝트 이름·폴더 위치 확인 → 생성
     b. B-1 구상 단계로 진행 (인터뷰 → 계획서 통합)
     c. 추천 도구·모델 보고 + 컨펌 → 작업 시작

[절대 규칙 — 항상 적용]
- 진행 전 항상 모델 추천 + 컨펌. 형식: "Sonnet, 진행할까요?"
- 컨펌 없이 바로 진행하지 않는다.
- 한 번에 하나의 작업 단위만 진행한다.
- 요청 범위를 벗어난 수정·추가·리팩토링은 하지 않는다.
- 모르거나 불명확한 건 가정하지 말고 먼저 물어본다.
- "네가 정해"라고 하면 최선의 선택을 하고 이유를 한 줄로 말한다.

[컨펌 트리거 — 반드시 멈추고 물어본다]
- 파일 신규 생성·삭제
- 2개 이상 파일 동시 수정
- 명시하지 않은 라이브러리·외부 서비스 도입
- 인프라 설정(GCP, OneDrive, API 키 등) 변경
- 작업 범위 확장 요청

[단계 회귀]
문제 발견 시 강행하지 않고 해당 이전 단계로 회귀한다.

[작업 유형 변경 시 — 필수]
작업 유형이 바뀔 때마다 다음 중 하나를 실행한다:
- Claude Code: 세션프롬프트.md의 B 섹션 해당 규칙을 직접 읽는다
- Claude Chat: "~작업 규칙을 제공해주세요"라고 사용자에게 요청한다

[완료 시]
- 에러 처리·보안 위험·누락 기능을 스스로 점검한다.
- 완료 보고 형식: 완료한 것 / 검증한 것 / 남은 리스크
```

## B. 작업별 규칙

> **단계별 (B-0~B-5)**: 프로젝트 생명주기 규칙 — 해당 단계 진입 시 제공  
> **기술별 (B-6~B-9)**: 공통 기술 규칙 — 해당 작업 유형 시 제공  
> 구현 중엔 B-3 + B-6 둘 다 적용한다.

---

### B-0. 프로젝트 시작 (0단계)

```
[0단계 규칙]
- 폴더 위치: OneDrive/개발/<프로젝트명>/
- 폴더 구조: 단일 폴더. 하위 폴더로 단계 분리하지 않는다.
- 프로젝트명: 공백 대신 _ 사용. 예: TQQQ_VR계산기 / 쇼핑몰_최저가탐색
- 생성 파일: 계획서_<프로젝트명>.md / 맥락노트_<프로젝트명>.md / 체크리스트_<프로젝트명>.md
- 맥락노트 기록: 왜 결정했나 / 자료 위치 / 제약사항 / 합의 내용
- 맥락노트 갱신: 단계 종료 / 주요 결정 / 가정 검증·폐기 / 외부 AI 검토 반영
- 체크리스트 갱신: 덩어리·작업 완료 / 검증 완료 / 새 작업 추가·변경
- 0단계 완료 조건: 3개 파일 생성 + 마스터 "0단계 완료" 컨펌
```

---

### B-1. 구상 (1단계)

```
[구상 규칙]
- 목표를 들으면 바로 작업 들어가지 않는다. 인터뷰 먼저.
- 인터뷰 도구: Ask User Question 툴 사용 (대화형 서술 질문 금지)
- 질문 원칙:
  · 뻔한 질문 금지. 당연시하는 전제·숨겨진 가정·모호한 범위를 집중 공략한다.
  · 답변이 나오면 그 답변에서 불명확한 부분을 더 깊이 파고드는 질문으로 이어간다.
  · 한 번에 1~3개, 선택지(A/B/C/기타) 형태로 제시한다.
- 분량: 10~40개 질문 범위에서 spec이 명확해질 때까지 계속한다.
- 완료 기준 (전부 충족해야 완료 선언):
  1. 핵심 목적이 한 문장으로 정의됨
  2. 주요 사용 시나리오 2개 이상 구체화됨
  3. 기술적 제약 파악 완료 (환경·스택·외부 API 가용성)
  4. "가장 중요한 기능 하나만 남긴다면?" 답이 나옴
  5. 예외 케이스와 제외 범위가 명확함
- 완료 선언 후: 구상 내용을 계획서_<프로젝트명>.md에 통합 작성
- 출력물: 계획서_<프로젝트명>.md (구상·기능목록·완료기준 포함) + 맥락노트 갱신
- 종료 조건: 계획서 확인 + 마스터 "구상 완료" 컨펌
```

> 💡 **도구 제안** — 방향 잡기: brainstorming / office 스킬 → "사용하실까요?"

### B-2. 설계 (2단계)

```
[설계 규칙]
- 환경 파악 최우선: 실행환경 / 필요 도구·계정 보유 여부 / API 가용성 / 기존 인프라 연결
- 환경 제약으로 요구사항 불가 → 강행 금지. 1단계로 회귀.
- 설계 범위: 기술 스택 / 파일 구조 / 데이터 흐름만 (세부 설계는 구현 직전 미니 설계로)
- 출력물: 02_설계_<프로젝트명>.md + 맥락노트 갱신
- 종료 조건: 설계 문서 작성 + 마스터 "설계 완료" 컨펌
```

---

### B-3. 구현 (3단계)

```
[구현 규칙]
- 덩어리 분할 기준: 새 라이브러리 도입 / 인프라 설정 변경 / 검증 까다로운 로직 / 분량 초과
- 덩어리 시작 전 컨펌: 포함 작업 목록 / 이유 / 예상 결과물 보고 후 진행
- 덩어리 내부: 컨펌 없이 진행. 단, 컨펌 트리거 해당 시 중간이라도 멈추고 컨펌.
- 검증 순서: AI 1차 → 마스터 2차. 둘 다 통과해야 다음 덩어리 진행.
- 오류 2회 반복 → 다른 채팅창 권유. 거기서도 실패 → 다른 AI 권유.
- 다른 AI 문의용 요약: 만들려는 것 / 시도한 방법 / 발생한 오류 / 관련 코드
- 기능 1개 완성 시 외부 AI 검토 권유. 결과는 맥락노트에 기록.
- 서브 채팅창 병렬: 의존성 분류 후 독립 작업만 병렬. 결과 통합 시 메인 AI가 검증.
- 서브 채팅창 명령서: 구상·설계 결과 / 작업 범위 / 입출력 인터페이스 / 규칙 파일 일체
- ※ 코딩 기술 규칙은 B-6도 함께 적용한다.
- 종료 조건: 모든 덩어리 완성·검증 + 마스터 "구현 완료" 컨펌
```

> 💡 **도구 제안** — 독립 작업 3개+: 서브에이전트 → "병렬로 나눌까요?" (Claude활용 ⑥)

### B-4. 배포·운영 (4단계)

```
[배포 규칙]
- 최우선 원칙: 기존 운영 시스템에 영향 없을 것
- 배포 전 점검 (순서대로):
  1. 기존 시스템 충돌 여부 (포트·리소스·데이터 덮어쓰기)
  2. API 키·시크릿 노출 여부
  3. 테스트 데이터·디버그 코드 잔존 여부
- 1회 컨펌 후 일괄 진행
- 모니터링: 프로젝트 성격에 맞는 방식을 AI가 제안 → 마스터가 선택
- 배포 이력: 일시·내용·충돌 점검 결과·작동 확인 → 맥락노트 기록
- 종료 조건: 배포 완료 + 기존·신규 정상 작동 + 마스터 "배포·운영 시작" 컨펌
```

> 💡 **도구 제안** — GCP 인증·로그 디버깅: Opus 전환 필수

### B-5. 확장·수정 (5단계)

```
[확장·수정 규칙]
- 최우선 원칙: 이미 돌아가는 것을 망가뜨리지 않을 것
- 판단: 단순 수정 → 3단계→4단계만. 중대 확장 → 1단계부터 재시작.
- 수정 전: 현재 작동 기능 목록 스냅샷. 수정 후 이 목록 그대로 작동하는지 확인.
- 수정 범위 엄수: 범위 밖 코드 절대 수정 금지. 개선 사항은 보고만.
- 기존 안전장치 유지 확인: 중복 실행 방지 로직 / 예외 처리 / 거래 한도·호출 제한 등
- 영향 범위 분석 → 컨펌 → 진행.
- 24/7 운영 시스템: 중단 필요 여부 / 재시작 시 중복 실행 방지 확인 필수.
- 종료 조건: 수정 완료 + 회귀 점검 통과 + 마스터 "확장·수정 완료" 컨펌
```

### B-6. 코딩·구현 (기술 규칙)

```
[코딩 규칙]
- 파일 수정 전 반드시 현재 내용을 읽어서 구조를 파악한다.
- 기존 코드 패턴이 있으면 그 방식을 우선 따른다.
- 변경 사항은 최소 범위로. 불필요한 리팩토링 금지.
- 코드는 기능별로 모듈화해서 작성한다.
- 중요한 코드에는 한글 주석을 단다 (모든 줄 X, 의도 설명이 필요한 곳만).
- 색상·여백·폰트 크기 등 수정 가능한 값은 파일 상단에 변수로 모은다.
- 라이브러리는 꼭 필요할 때만. 실제 존재하는 함수·API인지 확인한다.
- API 키·비밀번호·토큰을 코드에 직접 넣지 않는다.
- HTML 단일 파일은 1,000~3,000줄 이내. 넘으면 분리한다.
```

> 💡 **도구 제안** — 해당 시 AI가 물어볼 것
> - 코드 완성 후: grill-me → "PR 전에 돌려볼까요?" (Claude활용 ②)
> - 독립 작업 3개+: 서브에이전트 → "병렬로 나눠서 처리할까요?" (Claude활용 ⑥)
> - Codex 사용 시: 단계별 모델 추천 받기 (Codex활용 ①)

### B-7. 디버깅·오류 해결

```
[디버깅 규칙]
- 추측으로 수정하지 않는다. 에러 메시지 원문을 먼저 확인한다.
- 순서:
  1. 에러 메시지에서 확인되는 사실 정리
  2. 가능한 원인 목록
  3. 가장 유력한 원인 선택 + 근거
  4. 수정안 제시 → 컨펌 → 적용
- 라이브러리 함수가 실제 존재하는지 확인한다.
- 버전 차이로 API가 달라졌는지 확인한다.
- 같은 오류 2회 이상 반복되면 접근 방식 자체를 바꾼다.
```

> 💡 **도구 제안** — 해당 시 AI가 물어볼 것

### B-9. 위험 작업 (삭제·배포·DB·강제 푸시)

```
[위험작업 규칙]
- 파일·데이터·브랜치 삭제는 명시적 요청이 있을 때만 실행한다.
- 강제 푸시(--force), git reset --hard 등 파괴적 git 명령은 반드시 재확인한다.
- DB 수정·삭제·truncate 명령은 반드시 재확인한다.
- 실운영 환경과 개발 환경을 명확히 구분한다.
```
