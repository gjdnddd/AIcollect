# AI 일반 활용 가이드

> 어느 AI(Claude · GPT · Gemini 등)에서든 적용되는 작업 방법론.
> 도구가 달라도 그대로 쓸 수 있는 내용만 목적별로 모았다.

---

## ⓪ 기본 규칙 — 항상 적용

**무언가 진행하기 전 항상 컨펌을 받는다. 컨펌 요청 시 모델 추천을 반드시 함께 포함한다.**

형식:
```
Sonnet, 진행할까요?
Opus, 진행할까요?
```

- 컨펌 없이 바로 진행하지 않는다.
- 모델 추천 없이 컨펌 요청하지 않는다.

---

## ① 작업 시작하기 — 세션 시작 프로토콜

새 작업을 시작할 때 아래 순서로 진행한다. 질문은 한 번에 몰아 하지 않고 관련된 것끼리 묶어서 묻는다.

1. **목표 확인** — 사용자 말을 한 문장으로 요약해 확인
   - `"[요약한 목표]를 만드는 거 맞죠?"`
2. **기존 코드 확인** — 이미 만든 파일이 있으면 반드시 먼저 파악한 뒤 작업 범위 결정
3. **실행 환경 확인** — 결과물을 어떻게 쓸 것인가
   - 내 PC에서만 실행 / 브라우저에서 열기 / 인터넷에 올리기 / 자동으로 혼자 돌게
4. **완료 기준 확인** — "완성됐을 때 어떤 상태면 성공인가"
   - 사용자가 모르면 AI가 목표 기반으로 제안하고 확인받는다
5. **계획 제시 + 컨펌** — 코드 작성 전 반드시 계획을 제시하고 승인받는다

계획 제시 형식:

```
목표:        [한 줄 요약]
기술 스택:    A안 [이름-이유] / B안 [이름-이유]
추천:        [추천안 + 선정 이유 한 줄]
추천 모델:    [모델명 + 이유] / 인텔리전스 [낮음~매우높음]
주의사항:     [비용 / 계정·권한 / 난이도 / 차선책]
완료 기준:    [합의한 기준]
첫 작업:     [가장 작은 구현 단위]
진행할까요?
```

### 붙여넣기용 초기 지침 템플릿

새 작업 세션을 시작할 때 아래를 붙여넣는다.

```
너는 숙련된 풀스택 개발자야. 지금부터 아래 규칙을 반드시 따라줘.

[진행 방식]
- 도구선택가이드.md를 읽고 현재 단계에 맞는 도구·모델을 먼저 보고해줘.
- 세션 시작 질문은 하나씩 순서대로 해줘.
- 먼저 내 목표를 한 문장으로 요약해서 확인해줘.
- 기존 코드나 파일이 있는지 물어보고, 있으면 반드시 먼저 파악해줘.
- 결과물을 어떻게 사용할지 확인해줘.
- 완료 기준을 나와 합의해줘.
- 코드 작성 전에 반드시 계획과 추천 모델을 먼저 말하고 내 컨펌을 받아줘.
- 한 번에 하나의 작업 단위만 진행해줘.
- 모르거나 불명확한 건 가정하지 말고 먼저 물어봐줘.
- 내가 "네가 정해"라고 하면 네가 최선의 선택을 하고 이유를 한 줄로 말해줘.

[코드 작성 규칙]
- 코드는 기능별로 모듈화해서 작성해줘.
- 초보자도 이해하기 쉽게 중요한 코드에는 한글 주석을 달아줘.
- 색상·여백·폰트 크기 등 수정 가능한 값은 파일 상단에 변수로 모아줘.
- 라이브러리는 가장 가볍고 빠른 것을 우선 선택하고 이유를 알려줘.
- 사용하는 라이브러리 함수가 실제로 존재하는지 확인해줘.

[오류 발생 시]
- 추측으로 수정하지 말고 에러 메시지를 먼저 확인해줘.
- 원인을 설명하고 수정안을 제시한 뒤 컨펌 받고 적용해줘.

[완료 시]
- 에러 처리, 보안 위험, 누락 기능을 스스로 점검해줘.
- 가능한 테스트·빌드·실행 확인을 해줘.
```

## ② 맥락 잃지 않기 — 작업 기억 시스템

AI는 대화가 길어지면 초기 목표를 잊거나 딴 길로 샌다('금붕어 기억력'). 기억을 외부 문서로 빼둔다.

### 3종 외부 기억 문서

- **계획서** — 무엇을 만들 것인가 (설계도). 기능 목록·기술 스택·화면/API 구조·완료 기준
- **맥락노트** — 왜 이렇게 결정했고 자료는 어디 있는가. 제약사항·합의 내용
- **체크리스트** — 무엇을 끝냈고 무엇이 남았는가. 완료/진행중/남은 작업·검증 상태

> 계획이 승인되면 바로 코딩하지 말고 먼저 문서를 저장한다. 이후 새 세션을 열어 그 문서를 읽고 작업을 이어간다.

### 문서 계층 분리 (토큰 절약)

전체 매뉴얼을 매번 읽으면 토큰 소모가 크다. 계층을 나눈다.

- **마스터 매뉴얼** — 전체 원본 규칙. 새 프로젝트 시작 시에만 읽음
- **세션 규칙 요약본** — 현재 프로젝트 핵심 규칙. 자주 읽음. 마스터 매뉴얼을 처음 읽을 때 함께 생성
- **작업 문서(맥락노트·체크리스트)** — 작업 단위마다 읽고 업데이트

### 읽기 주기

| 문서 | 읽는 시점 |
|---|---|
| 마스터 매뉴얼 | 가끔 — 새 프로젝트 시작, 규칙 크게 변경, AI가 규칙 위반 시 |
| 세션 규칙 요약본 | 자주 — 새 세션, 작업 재개, 코드 작성 전, 파일 3개+ 수정 전, 오류 2회+ 반복, 위험 작업 전 |
| 맥락노트·체크리스트 | 가장 자주 — 작업 단위 시작 전/완료 후, 대화가 길어질 때 |

### 자동 매뉴얼 시스템 (분야별 분리)

프로젝트가 커지면 분야별로 매뉴얼을 쪼갠다 (frontend / backend / database / design / testing 등). 각 매뉴얼에 **활성화 키워드 · 적용 의도 · 적용 위치 · 확인할 패턴**을 적어두고, 작업 시작 전 요청 내용과 파일 위치를 보고 관련 매뉴얼만 먼저 확인한다.

## ③ 코드 잘 짜기 — 코드 작성 기준

### 공통

- 기능별로 코드를 나눈다. **한 번에 하나의 변경 단위**만 진행한다.
- 복잡한 로직·설정값·의도 설명이 필요한 곳에만 한글 주석 (모든 줄 X)
- 색상·여백·폰트 크기 등 자주 바뀌는 값은 파일 상단 변수로 모은다.
- 라이브러리는 꼭 필요할 때만. 쓸 경우 실제 존재하는 함수·API인지 확인한다.
- 초반부터 과한 추상화는 피한다. 같은 코드가 반복되면 그때 함수로 묶는다.

### 기술 스택 선택 기준

실행하기 쉬운가 / 규모에 맞는가 / 유지보수가 쉬운가 / 불필요한 설치·계정이 필요한가 / 속도·용량이 적절한가.
사용자가 지정하지 않으면 후보 2안을 제시하고 추천한다.

### 보안

- API 키·비밀번호·토큰을 **코드에 직접 넣지 않는다.**
- `.env` 파일은 커밋하지 않는다. 변수명만 `.env.example`이나 문서에 기록한다.
- 로그인·결제·개인정보·외부 API 코드는 특히 보수적으로 처리한다.

### HTML 단일 파일 프로젝트

- 한 파일은 1,000~3,000줄 이내. 넘으면 분리한다.
- 섹션 주석으로 구조 표시: `<!-- ===== [HEADER] 상단 타이틀 ===== -->`
- 섹션 ID는 파일 안에서 고유. 의존 관계는 주석에 명시.
- 수정 요청은 줄 번호 대신 **섹션 ID**로 한다.
- `structure.md`로 파일 구조 맵을 관리한다.
- 작업 순서: HTML 뼈대 → CSS 디자인 → JavaScript 동작 → 저장/검증.

### Git

- 작업 전 `git status`로 상태를 확인한다.
- 기존 변경사항·관련 없는 변경은 임의로 건드리지 않는다.
- 커밋·브랜치 생성·푸시는 사용자가 명시적으로 요청할 때만.
- 브랜치 이름은 도구명 prefix 사용 (예: `codex/`, `claude/`).
- 커밋 메시지: `type: short summary` (feat / fix / refactor / test)

## ④ 문제 해결하기 — 디버깅 · 품질 검사

### 디버깅 3단계

1. **증거 수집** — 에러 메시지를 그대로 확보한다.
   - 브라우저: F12 → Console 탭 → 빨간 에러 전체 복사
   - 서버/터미널: 출력된 에러 전체 복사
2. **원인 분석** — 추측으로 바로 고치지 않는다. 순서대로 설명한다.
   - 에러에서 확인되는 사실 → 가능한 원인 → 가장 유력한 원인 → 수정안 → 적용 컨펌
3. **교차 검증** — 원인이 불확실하면 확인한다.
   - 라이브러리 함수가 실제 존재하는가 / 버전 차이로 API가 달라졌는가 / 실행 환경 제한이 있는가 / 같은 오류가 재현되는가

### 완료 전 셀프 체크

- 에러 처리가 필요한 곳에 처리했는가
- 보안상 위험한 코드가 없는가
- 누락된 기능이 없는가
- 사용자가 말한 완료 기준을 충족하는가
- 모바일/데스크톱 화면에서 텍스트가 겹치지 않는가
- 테스트·타입 체크·빌드 중 가능한 검증을 실행했는가

### 완료 보고 형식

```
완료:      [무엇을 변경했는지]
검증:      [실행한 테스트/빌드 + 통과 여부]
셀프 체크:  에러 처리 / 보안 위험 / 누락 기능
참고:      [남은 리스크, 사용자가 확인하면 좋은 부분]
```

> "다 했습니다" 식의 답변 금지. 검증을 실행하지 못했으면 그 이유를 보고에 남긴다.

## ⑤ 토큰 절약하기 — 출력 압축 도구 (Caveman)

AI 에이전트의 장황한 답변을 압축해 토큰 비용을 줄이는 오픈소스 도구.  
Claude Code · Cursor · Codex 등 여러 에이전트에 공통 적용 가능.

### 압축 모드 4단계

| 모드 | 설명 | 절약 |
|---|---|---|
| Light | 인사말·맺음말만 제거 | 소폭 |
| Full | 핵심 단어·코드 위주 (기본값) | 평균 65% |
| Ultra | 단어 단위로 극단 압축 | 최대 87% |
| Wean | 한문체 출력 (실험적) | — |

### 설치 및 사용

```bash
# Claude Code (VS Code 터미널)
curl -fsSL https://raw.githubusercontent.com/ajkachnic/caveman/main/install.sh | bash

# Codex (Windows PowerShell)
irm https://raw.githubusercontent.com/ajkachnic/caveman/main/install.ps1 | iex
```

```
# 원시인 모드 켜기
> caveman

# 극단 압축
> caveman ultra

# 일반 모드 복귀
> normal mode
```

### 메모리 파일 압축 (영구 절약)

```bash
# 프로젝트 루트에서 실행 — 규칙·맥락 파일 평균 46% 압축
caveman compress
```

## ⑥ 데이터 보호 — AI 도입 시 DB 보호 가이드라인

AI 에이전트가 실운영 DB를 건드려 데이터가 증발하는 사고를 방지하는 3대 원칙.

### 1. 실운영과 개발 환경 물리적 격리

- AI가 접근하는 환경에 Production DB 접속 정보를 절대 노출하지 않는다.
- 스키마만 동일한 **개발용 DB(Mock Data)**를 별도 구축해 연결한다.
- `.env` 파일(API 키, DB 패스워드)은 `.gitignore`에 포함, AI 컨텍스트에 넣지 않는다.

### 2. 백업의 3-2-1 법칙

- 백업 DB는 실운영 DB와 **다른 클라우드 계정·독립 네트워크**에 보관한다.
- Object Storage의 **버전 관리·불변성(WORM)** 옵션 활성화 → AI 삭제 명령 물리 거부.

### 3. Human-in-the-Loop (인간 개입 승인)

- AI가 `rm`, `drop`, `truncate` 등 파괴적 명령 실행 시 **[y/N] 승인 프로세스를 절대 생략하지 않는다.**
- AI 수정 결과는 `feature/ai-work` 브랜치에 커밋 → PR 코드 리뷰 통과 후에만 메인 합류.
- **프롬프트 수준의 방어("절대 지우지 마")는 강제력이 없다.** 아키텍처·권한으로만 방어한다.

## ⑦ 다양한 AI와의 협업 — 멀티 에이전트

작업 규모가 크거나(프론트·백엔드 동시 변경 등) 검토가 중요할 때(보안·결제·인증) 역할을 분담한다.

### 역할 분리

- **구현 담당** — 기능 구현, 기존 코드 패턴 준수
- **리뷰 담당** — 버그·보안·테스트 누락 확인
- **테스트 담당** — 재현 방법 확인, 테스트 케이스 제안
- **문서 담당** — README·사용법·체크리스트 정리

### 교차 검증

한 모델이 작성한 코드를 **다른 모델로 검수**한다 (예: Claude 작성 → GPT 검수). 동일 모델 관점에서 놓치는 사각지대를 타사 모델 시각으로 상호 보완한다.

### 보고 형식 의무화

에이전트에게는 반드시 구체적 보고 형식을 준다.

> "무엇을 발견했고, 무엇을 수정했고, 왜 그렇게 판단했는지 보고서로 정리해줘."

## ⑧ 하네스 마스터 로드맵 — 최소 결정만 하고 AI에게 나머지 맡기기

> "나는 결정만 한다. AI는 나머지 전부를 한다."

AI를 활용한 프로젝트에서 사용자는 아이디어와 기술 선택만 하고, 나머지(기술 검색, 설계, 구현, 배치)는 모두 AI에게 맡기는 프로세스. 초고성능 하네스(Cursor Rules, Claude Rules 등)를 통해 AI의 반복 실수를 원천 차단.

### 핵심 철학

- **역할 분리**: 당신 = 결정자 (아이디어·최종 선택), AI = 실행자 (검색·설계·코딩)
- **하네스 고착**: 선택한 규칙을 `.claude/rules/`, `.cursor/rules/`, `.cline/rules.md` 등 파일로 고착 → 자동 적용
- **돌발 명령**: 코딩 중 "이 에러 재발 방지 규칙 추가", "성능 최적화 조건 추가" 등으로 하네스 자체를 진화시킴

### 4단계 프로세스

#### **1단계: 아이디어 + 기술스택 추천 받기**

프롬프트:
```
나 바이브 코딩으로 [만들고 싶은 프로그램]을 만들고 싶어.

요청:
1. 이걸 만들기에 가장 쉬운 기술 스택 추천
2. 개발 단계 및 계획
3. 나중에 글로벌 하네스(cursorrules.org, GitHub) 검색할 때 쓸 '핵심 기술 키워드' 리스트

응답 형식:
## 기술 스택
- 언어: 
- 프레임워크:
- 주요 라이브러리:
- 선정 이유:

## 개발 단계 (5단계 max)
1. [단계명]: [상세]
...

## 하네스 키워드
- keyword1
- keyword2
...
```

#### **2-3단계: 글로벌 하네스 후보 비교 및 선택**

AI에게 이 키워드로 **cursorrules.org**, **GitHub** 등에서 별⭐ 많은 하네스 3개를 찾아달라고 요청.

AI가 표로 정리한 후보 3개 중 하나를 선택하면, AI가 선택한 하네스의 **전체 텍스트를 복사**해준다.

#### **4단계: AI에게 하네스 파일 자동 배치 + 코딩 시작**

프롬프트:
```
너는 지금 [Claude Code / Cursor / Cline / 기타]의 시니어 개발자 AI야.

이 도구에 맞는 하네스 파일 위치를 먼저 확인하고, 
아래 선택한 하네스를 그 위치에 파일로 생성해줘. (UTF-8 인코딩)

배치 후:
✅ 하네스 세팅 완료. 코딩 시작해도 됩니다.
라고 알려줘.

[여기에 선택한 하네스 본문 전체 붙여넣기]
```

### 하네스 파일 위치 (도구별)

| 도구 | 경로 | 포맷 |
|---|---|---|
| **Claude Code** | `.claude/rules/` | `.md` 또는 `.txt` |
| **Cursor** | `.cursor/rules/` 또는 `.cursorrules` | `.md` |
| **Cline** | `.cline/rules.md` | `.md` |
| **Aider** | `.aider.rules.md` | `.md` |
| **기타 IDE** | `.rules/` | `.md` |

### 코딩 중 돌발 명령 (하네스 자체를 진화시키기)

**상황: 같은 에러 반복**
```
너 또 똑같은 실수했어. 
지금 하네스 규칙 파일에 이 에러를 영구적으로 막는 '금지 규칙' 한 줄 추가해줘:

[구체적 금지 조건을 한 문장으로]

그리고 다시 코딩해.
```

**상황: 자동 테스트 연동 필요**
```
이 기능이 오류 없이 작동하는지 중간중간 자동으로 테스트하게 해.
테스트 항목들을 하네스에 추가해줘.

테스트 1: ~
테스트 2: ~
```

**상황: 스코프 변경**
```
원래 계획 변경: [제거할 기능] 빼고 [새 기능] 추가.
하네스 규칙 업데이트해줘.

변경사항:
- 제거: [기능]
- 추가: [기능]
- 우선순위 변경: [기능 A] > [기능 B]
```

### 프로젝트 완성 시 폴더 구조

```
my-project/
├── .claude/
│   └── rules/
│       ├── core-rules.md         (선택한 초고성능 하네스)
│       ├── no-repeat-errors.md   (돌발 금지 규칙)
│       ├── test-rules.md         (자동 테스트 규칙)
│       └── style-guide.md        (스타일 규칙)
├── README.md                      (하네스 설명 섹션)
├── src/
│   └── ...
└── ...
```
