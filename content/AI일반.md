# 1부. 알아야 할 내용

> 사용 시점: 처음 읽기 / AI가 이상한 행동을 할 때 근거 확인용  
> 사용자가 읽는 파트. AI에게 직접 줄 필요 없음.

## ① AI 특성·한계

### 기억 문제
- **대화 내 망각**: 대화가 길어지면 앞 내용을 잊거나 요약 처리된다.
- **대화 간 망각**: 새 대화를 시작하면 이전 대화 내용을 모른다.
- **대응**: 중요한 규칙·컨텍스트는 파일로 저장하고 매 세션 시작 시 제공한다.

### 맥락 창(Context Window) 한계
- 한 번에 처리할 수 있는 텍스트 양에 한계가 있다.
- 대화가 너무 길면 자동 요약이 발생하고 세부 내용이 손실된다.
- **대응**: 긴 작업은 세션을 나누고, 핵심 정보는 파일로 관리한다.

### 자의적 행동
- 명시적 승인 없이 코드 수정·파일 생성 등을 진행할 수 있다.
- **대응**: 기본 규칙의 컨펌 형식 적용 (`Sonnet, 진행할까요?`)

### 환각(Hallucination)
- 없는 함수·파일·API를 있다고 말하거나 잘못된 정보를 자신 있게 제시한다.
- **대응**: 중요한 사실은 직접 코드·문서를 읽어 검증한다. "기억한다"와 "지금 확인했다"를 구분한다.

### 과잉 친절 (Over-engineering)
- 단순한 수정을 요청했는데 전체 구조를 바꾸거나 요청하지 않은 기능을 추가한다.
- 에러 처리·예외 케이스·확장성까지 알아서 넣어 결과물이 과도하게 복잡해진다.
- **대응**: "한 번에 하나의 작업 단위만" 규칙을 명시적으로 준다. 범위를 구체적으로 지정한다. ("이 함수만", "이 파일만")

## ③ AI 코딩 원칙 (카파시 4원칙)

*출처: 안드레이 카파시(Andrej Karpathy) Vibe Coding 가이드*

**AI 코딩 3대 고질병 — 명령만 내렸을 때 발생하는 실패 패턴**

1. **잘못된 가정** — 모호한 점을 묻지 않고 혼자 결론 내려 엉뚱한 방향으로 수백 줄 작성
   - 예: "로그인 기능 만들어줘" → 세션 쿠키 원했으나 묻지도 않고 JWT 인증 시스템 통째로 구축
2. **코드 부풀리기** — 문제를 과도하게 해석해 불필요한 추상 인터페이스·옵션 클래스 도입
   - 예: "이메일 형식 검증해줘" → 간단한 정규식 대신 거대한 검증 클래스와 8개 옵션 파라미터 생성
3. **멋대로 고치기** — 요청 외 인접 코드·포매팅·주석을 'AI가 보기에 더 깔끔하다'며 수정
   - 결과: 멀쩡히 돌아가던 기능이 망가지고, Diff가 수십 개로 늘어 리뷰 불가

**4대 원칙**

| 원칙 | 한 줄 요약 | 핵심 행동 |
|---|---|---|
| 먼저 생각하라 | 가정 말고, 헷갈리면 물어라 | 이해한 내용 먼저 선언 → 해석 여러 개면 질문 → 단순 대안 있으면 제안 |
| 단순하게 먼저 | 최소 코드만, 추측성 코드 배제 | 시키지 않은 기능 추가 금지, 과한 추상화 금지, 200줄→50줄 가능하면 다시 짜기 |
| 외과 수술처럼 | 타겟 코드만 고쳐라 | 인접 코드 포매팅·주석 손대지 않기, 고장 안 난 코드 리팩토링 금지 |
| 목표 중심 실행 | 검증 가능한 목표를 주고, 달성까지 반복 | 버그 수정 시 재현 테스트 먼저 → 통과 후 수정, 단계별 계획 선언 후 실행 |

# 2부. 세션 시작

> 사용 시점: 매 세션 시작 / **세션프롬프트 A·C의 원본**  
> 실제 붙여넣기 텍스트 → 세션프롬프트.md > A 참고

## ① 기본 규칙

모든 작업에 항상 적용되는 절대 규칙. AI가 어길 때마다 리마인드한다.

- 진행 전 항상 **모델 추천 + 컨펌**. 형식: `"Sonnet, 진행할까요?"`
- 컨펌 없이 바로 진행하지 않는다.
- **범위 준수**: 요청 범위를 벗어난 리팩토링·기능 추가는 하지 않는다. 개선 발견 시 보고만.
- **검토 먼저**: 파일 수정 전 반드시 읽어서 구조 파악 후 제안한다.
- **외부 서비스** (GCP·GitHub 등): 비용 발생·파괴적 작업은 반드시 사전 확인.
- 모르거나 불명확한 건 가정하지 말고 먼저 질문한다.
- `"네가 정해"`라고 하면 최선의 선택을 하고 이유를 한 줄로 말한다.

---

## ② 작업 기억 시스템

> 세션프롬프트 C의 원본

AI는 대화가 길어지면 초기 목표를 잊는다. 기억을 외부 문서로 관리한다.

### 3종 문서

| 문서 | 내용 | 갱신 시점 |
|---|---|---|
| `계획서_<프로젝트명>.md` | 기능 목록·기술 스택·완료 기준 | 계획 변경 시 |
| `맥락노트_<프로젝트명>.md` | 결정 이유·제약사항·합의 내용 | 주요 결정마다 |
| `체크리스트_<프로젝트명>.md` | 완료·진행중·남은 작업 | 작업 단위마다 |

> 계획 승인 후 바로 코딩하지 않는다. 먼저 3종 문서를 만들고 새 세션에서 읽어서 이어간다.

세션 이어가기 프롬프트:
```
계획서, 맥락노트, 체크리스트를 먼저 읽고 이어서 진행해줘.
```

### 문서 계층 분리 (토큰 절약)

- **마스터 매뉴얼** — 전체 원본. 새 프로젝트 시작 시에만 읽음
- **세션 규칙 요약본** — 핵심 규칙. 자주 읽음. 마스터 매뉴얼 처음 읽을 때 함께 생성
- **작업 문서** — 작업 단위마다 읽고 업데이트

### 규칙 재주입 시점

| 상황 | 해야 할 것 |
|---|---|
| 새 채팅창 열 때 | 세션프롬프트 A 붙여넣기 |
| 작업 유형 바뀔 때 | 세션프롬프트 B 해당 규칙 제공 |
| 대화 20~30턴 이상 | 레벨 2 리마인드 던지기 |
| AI가 규칙 어기기 시작 | 레벨 1 즉각 던지기 |

## ③ 목표 인터뷰

사용자가 목표를 말하면 계획 전에 인터뷰로 니즈를 먼저 파악한다.  
사용자는 저장 방식·구현 방법까지 다 생각하고 오지 않아도 된다.  
AI가 질문을 통해 구체화한다.

### 인터뷰 항목 (최대 5개, 한 번에 몰아 묻지 않고 흐름에 맞게)

| 항목 | 확인 내용 |
|---|---|
| 목표 확인 | 말한 것을 한 문장으로 재요약해 확인 |
| 저장·보관 방식 | 어디에, 어떤 형식으로 남길지 (모르면 AI가 제안) |
| 기존 파일·코드 유무 | 이미 있는 게 있는지 → 있으면 먼저 읽음 |
| 실행 환경 | PC / 브라우저 / 서버 / 자동화 |
| 완료 기준 | 성공 상태 합의 (모르면 AI가 제안) |

### 인터뷰 → 보고 → 계획 순서

1. **인터뷰** — 대화 흐름에 맞게 항목 확인 (질문 5개 이내)
2. **정리 보고** — 확인된 내용 요약:
   ```
   목표:       [한 줄]
   저장 방식:  [결정된 것]
   기존 파일:  [있음 / 없음]
   실행 환경:  [선택된 것]
   완료 기준:  [합의된 것]
   ```
3. **계획 제시** — 모델 추천 + 컨펌

# 3부. 작업 유형별 규칙

> 사용 시점: 해당 작업 시작 시 / **세션프롬프트 B의 원본**  
> 각 섹션 구조: **원칙 → 이유 → 행동 지침**

## ① 코드 작성
> → 세션프롬프트 B-6

**원칙**: 변경은 최소 범위로. 요청한 것만 고친다.

**이유**: 멀쩡한 코드를 건드리면 Diff가 늘어나 리뷰가 불가능해지고 의도하지 않은 버그가 생긴다.

**행동 지침**:
- 파일 수정 전 반드시 현재 내용을 읽어서 구조를 파악한다.
- 기존 코드 패턴이 있으면 그 방식을 우선 따른다.
- 변경 사항은 최소 범위. 불필요한 리팩토링 금지.
- 코드는 기능별로 모듈화해서 작성한다.
- 중요한 코드에는 한글 주석 (모든 줄 X, 의도 설명이 필요한 곳만).
- 색상·여백·폰트 크기 등 수정 가능한 값은 파일 상단에 변수로 모은다.
- 라이브러리는 꼭 필요할 때만. 실제 존재하는 함수·API인지 확인한다.
- API 키·비밀번호·토큰을 코드에 직접 넣지 않는다.
- HTML 단일 파일은 1,000~3,000줄 이내. 넘으면 분리한다.

**기술 스택 선택 기준**: 실행하기 쉬운가 / 규모에 맞는가 / 유지보수가 쉬운가 / 불필요한 설치·계정이 필요한가.  
사용자가 지정하지 않으면 후보 2안을 제시하고 추천한다.

**Git**:
- 작업 전 `git status`로 상태 확인.
- 커밋·브랜치 생성·푸시는 명시적 요청 시에만.
- 커밋 메시지: `type: short summary` (feat / fix / refactor / test)

## ② 디버깅
> → 세션프롬프트 B-7

**원칙**: 추측으로 수정하지 않는다. 증거를 먼저 수집한다.

**이유**: 원인 모르고 수정하면 다른 버그가 생기고 시간이 두 배로 든다.

**행동 지침**:
- 에러 메시지 원문을 먼저 확인한다.
- 순서:
  1. 에러에서 확인되는 사실 정리
  2. 가능한 원인 목록
  3. 가장 유력한 원인 + 근거
  4. 수정안 제시 → 컨펌 → 적용
- 라이브러리 함수가 실제 존재하는지 확인한다.
- 버전 차이로 API가 달라졌는지 확인한다.
- 같은 오류 2회 이상 반복되면 접근 방식 자체를 바꾼다.

**완료 보고 형식**:
```
완료:      [무엇을 변경했는지]
검증:      [실행한 테스트/빌드 + 통과 여부]
셀프 체크: 에러 처리 / 보안 위험 / 누락 기능
참고:      [남은 리스크]
```

## ③ 외부 서비스 연동 (GCP, GitHub 등)
> → 세션프롬프트 B-8

**원칙**: 비용·권한·파괴적 결과가 있는 작업은 반드시 사전 확인한다.

**이유**: 실수 시 복구 불가 또는 예상치 못한 비용 발생.

**행동 지침**:
- 비용이 발생할 수 있는 작업은 실행 전 반드시 확인한다.
- 실제 네트워크 요청·API 호출은 사용자 확인 후 진행한다.
- GCP IAM·인증 문제 → Opus 모델 사용.
- 배포 실패 원인 분석·로그 디버깅 → Opus 모델 사용.

---

## ④ 위험 작업 (삭제·배포·DB·강제 푸시)
> → 세션프롬프트 B-9

**원칙**: 파괴적 명령은 명시적 요청이 있을 때만, 반드시 재확인한다.

**이유**: 삭제·강제 푸시는 복구가 불가능하거나 매우 어렵다.

**행동 지침**:
- 파일·데이터·브랜치 삭제는 명시적 요청이 있을 때만 실행한다.
- 강제 푸시(--force), `git reset --hard` 등 파괴적 git 명령은 반드시 재확인한다.
- DB 수정·삭제·truncate 명령은 반드시 재확인한다.
- 실운영 환경과 개발 환경을 명확히 구분한다.
- 금전·운영 리스크가 있는 결정 → Opus 모델 사용.

---

## ⑤ 문서·정리
> → 세션프롬프트 B-10

**원칙**: 원본의 핵심 내용이 손실되지 않도록 한다.

**이유**: 요약 과정에서 행동 규칙·조건·기준이 사라지면 문서의 의미가 없어진다.

**행동 지침**:
- Haiku 모델로 진행한다.
- 기존 파일 덮어쓰기 전 내용을 먼저 읽어서 확인한다.
- 행동 규칙·조건·기준은 원문 그대로 유지한다. 배경·목적은 요약 가능.
- 원본 파일이 잘리거나 불완전하면 통합 전에 먼저 보고한다.

## ⑥ 데이터 보호
> AI 도입 시 DB 보호 가이드라인

**원칙**: AI가 실운영 DB에 접근하지 못하게 물리적으로 격리한다.

**이유**: 프롬프트 수준의 방어("절대 지우지 마")는 강제력이 없다. 아키텍처·권한으로만 방어한다.

**행동 지침**:
- AI가 접근하는 환경에 Production DB 접속 정보를 절대 노출하지 않는다.
- 스키마만 동일한 개발용 DB(Mock Data)를 별도 구축해 연결한다.
- `.env` 파일은 `.gitignore`에 포함, AI 컨텍스트에 넣지 않는다.
- 백업 DB는 실운영 DB와 다른 클라우드 계정·독립 네트워크에 보관한다.
- Object Storage의 버전 관리·불변성(WORM) 옵션 활성화.
- AI가 `rm`, `drop`, `truncate` 등 파괴적 명령 실행 시 [y/N] 승인 프로세스를 절대 생략하지 않는다.
- AI 수정 결과는 `feature/ai-work` 브랜치에 커밋 → PR 코드 리뷰 통과 후에만 메인 합류.

## ⑦ 프로젝트 관리
> → 세션프롬프트 B-0~B-5

**원칙**: 단계를 밟되, 문서로 기억을 대신한다.

**이유**: 구현에 바로 뛰어들면 방향이 틀렸을 때 전부 다시 만든다. 단계별 컨펌이 낭비를 막는다. AI는 대화가 끊기면 기억을 잃으므로 3종 문서 없이는 재개가 불가능하다.

**행동 지침**:
- 새 프로젝트: 0단계부터 시작 (폴더 생성 → 인터뷰 → 3종 문서 생성). 문서 없이 구현 진입 금지.
- 단계마다 종료 조건 확인 후 다음 단계 진입.
- 구현 중(3단계): 덩어리 분할 + 검증 순서 준수. B-6 코딩 기술 규칙과 병행.
- 기존 프로젝트 재개: 3종 문서 먼저 읽고 현재 단계·상태 파악 후 진행.
- 문제 발견 시 강행 금지. 해당 이전 단계로 회귀.

**단계 구조 요약**:

| 단계 | 이름 | 핵심 원칙 |
|---|---|---|
| 0단계 | 프로젝트 시작 | 폴더·3종 문서 셋업 |
| 1단계 | 구상 | AI 주도 인터뷰로 구체화 |
| 2단계 | 설계 | 환경 파악 → 기술 스택 → 구조 결정 |
| 3단계 | 구현 | 덩어리 분할·검증 (B-3 + B-6 병행) |
| 4단계 | 배포·운영 | 기존 시스템에 영향 없을 것 |
| 5단계 | 확장·수정 | 작동하는 것을 망가뜨리지 않을 것 |

## 멀티 에이전트 — 다양한 AI와의 협업

작업 규모가 크거나(프론트·백엔드 동시 변경 등) 검토가 중요할 때 역할을 분담한다.

| 역할 | 담당 |
|---|---|
| 구현 담당 | 기능 구현, 기존 코드 패턴 준수 |
| 리뷰 담당 | 버그·보안·테스트 누락 확인 |
| 테스트 담당 | 재현 방법 확인, 테스트 케이스 제안 |
| 문서 담당 | README·사용법·체크리스트 정리 |

한 모델이 작성한 코드를 **다른 모델로 검수**한다 (예: Claude 작성 → GPT 검수).

에이전트에게는 반드시 구체적 보고 형식을 준다:
> "무엇을 발견했고, 무엇을 수정했고, 왜 그렇게 판단했는지 보고서로 정리해줘."

## 하네스 마스터 로드맵 — 최소 결정만 하고 AI에게 나머지 맡기기

> "나는 결정만 한다. AI는 나머지 전부를 한다."

AI를 활용한 프로젝트에서 사용자는 아이디어와 기술 선택만 하고, 나머지(기술 검색, 설계, 구현, 배치)는 모두 AI에게 맡기는 프로세스.

**핵심 철학**:
- **역할 분리**: 당신 = 결정자 (아이디어·최종 선택), AI = 실행자 (검색·설계·코딩)
- **하네스 고착**: 선택한 규칙을 `.claude/rules/`, `.cursor/rules/` 등 파일로 고착 → 자동 적용
- **돌발 명령**: 코딩 중 "이 에러 재발 방지 규칙 추가"로 하네스 자체를 진화시킴

**4단계 프로세스**:

1. **아이디어 + 기술스택 추천 받기**
   ```
   나 바이브 코딩으로 [만들고 싶은 프로그램]을 만들고 싶어.
   1. 가장 쉬운 기술 스택 추천
   2. 개발 단계 및 계획
   3. 하네스 검색용 핵심 기술 키워드 리스트
   ```

2. **글로벌 하네스 후보 비교 및 선택** — cursorrules.org, GitHub에서 별⭐ 많은 하네스 3개 비교

3. **하네스 파일 자동 배치**
   ```
   너는 지금 [Claude Code / Cursor / Cline]의 시니어 개발자 AI야.
   이 도구에 맞는 하네스 파일 위치에 아래 하네스를 생성해줘.
   [선택한 하네스 본문 전체 붙여넣기]
   ```

4. **코딩 시작** — 하네스 규칙이 자동 적용된 상태로 진행

**하네스 파일 위치**:

| 도구 | 경로 |
|---|---|
| Claude Code | `.claude/rules/` |
| Cursor | `.cursor/rules/` 또는 `.cursorrules` |
| Cline | `.cline/rules.md` |

**하네스 저장소**:
- https://cursorrules.org
- https://github.com/search?q=cursor+rules

## 하네스 엔지니어링 — 성능 격차를 만드는 3가지 축

동일한 AI 모델과 예산을 투입해도 팀마다 결과물 수준이 갈리는 이유는 하네스 구성에 있다.

### ① 컨텍스트 엔지니어링
- 컨텍스트 윈도우는 무제한이 아니다. 300K 토큰 초과 시 품질 급락.
- 무조건 많이 넣기보다 **가치 높은 컨텍스트를 엄선**한다.
- **정적 컨텍스트** (세션 시작 시 필수): 목표·제약사항, 코딩 컨벤션, 보안 규정
- **동적 컨텍스트** (필요 시 호출): 수정 대상 코드, 에러 트레이스, 외부 문서
- 루트에 경량 목차 문서(CLAUDE.md)를 두고 세부 지식은 하위 폴더에 분리

### ② 환경 디자인
- **승인 기반 루프**: 초기에는 수동 승인으로 AI 행동 패턴 체감. 익숙해지면 샌드박스 활용.
- **샌드박스 검증**: AI 생성 코드를 로컬에 반영하기 전 샌드박스에서 검증.

### ③ 평가 기반 개선
- AI가 작성한 코드는 자동화된 평가 프로세스(테스트 통과율, 린팅 등)로 품질을 측정한다.
- **자기 편향 방지**: 작성 세션과 평가 세션을 반드시 분리해 교차 검증한다.
  예: Claude Code 작성 → Codex 검증 (Claude활용 ⑨ 참조)
